## 0. The one structural fact that reframes the whole review

The v2 shell gate is a **local variable read from an env var, once per frame**:

```rust
// app_update.rs:87
let ui_v2 = std::env::var("AZRA_UI").ok().as_deref() == Some("v2");
```

`ui_v2` exists **only** in `app_update.rs` (no other file references it). Gating is therefore purely a function of which calls sit in the `if ui_v2 { … }` arm (`app_update.rs:263`) versus the `else` arm (`app_update.rs:271`). The entire v1 properties chain hangs off `draw_right_panel(ctx)` at **`app_update.rs:287`, inside the `else` arm**.

Consequence: the reviewer's premise for its #1 priority item — that the v1 surfaces "coexist" and draw alongside the v2 panel — **does not hold**. This invalidates P0-1 as stated, and it also means several downstream "dual-write" worries are moot. But the audit surfaced a *different*, real v2 bug in the same area (see **NEW-1**), which is the item actually worth fixing.

## 2. What to fix FIRST — ranked, CONFIRMED items only

1. **NEW-1 — v2 cannot edit the material a fresh scene actually renders.** (P0) Not in the external review, but it is the real form of the problem it was groping at. Every new v2 scene hits it; the panel's own dead-end message points at two features rather than fixing the state. Highest user impact, self-contained.
2. **P0-3 — silent `Stub` lowering.** (P0) Directly matches the owner's "nothing happened" report. The decision function is already pure and already called in four places; this is a badge + hover text, no logic change. Best effort-to-relief ratio in the list.
3. **P0-4 — conflict badge is a dead pixel.** (P0) A user who hits a bake-ownership conflict gets an orange word with no hover, no click, and no explanation, while the recovery action sits behind an unrelated state gate in a right-click menu. Make the badge a widget; reuse the existing revert surgery.
4. **S6-b — MaterialId reuse + unpurged side tables.** (P1) Genuinely corrupting (a new material silently inherits a deleted one's doc and node graph), but rarer than 1–3 and the id-allocator half touches save format, so it needs the both-branches lockstep treatment. Do the side-table purge first — it is safe and independent.
5. **P1-2 — UV projection false-enable.** (P1) Real and verbatim-confirmed, but it mis-enables a combo rather than corrupting data. Note the fix needs a design call: material→object is many-to-many, so "does THIS object have UVs" is not a well-posed question for a shared material.

**Explicitly NOT worth fixing based on this review:** P0-1, P0-1a, P0-1b, P1-5 (refuted); P1-3 (working as designed, UI is honest); S6-a (not reachable through the UI). **P2-1** is a scope gap, not a bug — decide it as a feature.

- [ ] **LT-3 — S6-b, MaterialId reuse.** (gates the P1 fix; the destructive one)
