# Poly toolset — deep audit vs Blender

**Date:** 2026-07-30
**Owner asked:** review each poly tool in depth, assess functionality, and say what is missing vs Blender.
**Method:** 6 auditors (one per tool family) + an adversarial verifier per blocker/major claim. 45 agents.
**Coverage:** 56 existing tools assessed; 25 missing-tool claims (24 confirmed, 1 refuted).

All agents were read-only and pinned to the ui-polish worktree. No source file was modified.

---

## Headline

The poly kernel is **far stronger than the UI exposes**. Repeatedly the pattern is: the kernel op is
correct and oracle-tested against Blender, and the app layer either does not wire it, or hardcodes
its parameters. That is good news — the expensive half is done.

**Also worth saying plainly:** Circle / Flatten / Relax / Space / Bridge are *LoopTools*, which is an
**addon** in Blender, not vanilla. Having them working puts AZRA **ahead of stock Blender** there.

### Extrude/Inset selection resolution in Vertex and Edge mode  — `works-partial`

* **Severity:** blocker | **Verdict:** CONFIRMED
* **Where:** app/src/poly_selection.rs:1610 poly_faces_or_all (used by poly_drag_tools.rs:37 and :276, and poly/extrude.rs:70, poly/inset.rs:44). Gate: app/src/poly/key_dispatch.rs:12 and :33 both require `self.poly_work_mode == PolyWorkMode::Face && !self.poly_sel.selected_faces.is_empty()`. Armed-tool click gate: input_viewport.rs:1868 and :1873 require !selected_faces.is_empty().

**What it actually does.** The keyboard and click gates DO protect against the worst case: in Vertex or Edge mode, E and I only set self.poly_tool (key_dispatch.rs:18, :39) and never start a drag, and the armed-tool click path also requires a non-empty FACE selection. So there is no data-loss bug here. The 'Modo implicit full selection' fallback in poly_faces_or_all (:1616-1619 = every live face when nothing is selected) is reachable only from the one-shot menu/command paths (poly/extrude.rs:70, poly/inset.rs:44), where extruding/insetting everything is additive and reversible — documented as SAFE at extrude.rs:68-69.

**Gap vs Blender.** vs Blender: E works in ALL THREE select modes. Blender's Extrude Vertices (mesh.extrude_vertices_move) pulls new edges from selected verts; Extrude Edges (mesh.extrude_edges_move) pulls new faces from selected edges — both are core box-modelling moves (drawing a profile edge-loop and pulling it into a surface). AZRA has NEITHER: grep for extrude_vertices / extrude_edges / extrude_vert / extrude_edge across app/src and core_math/src returns zero hits. In vertex or edge mode, pressing E is a silent no-op that only arms a tool that can never fire (key_dispatch.rs:18 sets poly_tool = ExtrudeFace, then input_viewport.rs:1868 blocks it because selected_faces is empty). That is a dead key with no toast — the user gets no feedback at all.

**Verifier correction (authoritative).** Claim survives with one framing precision. The claim says E in vertex/edge mode arms 'a tool that can never fire' — strictly, the arming PERSISTS (key_dispatch.rs:18 sets poly_tool = ExtrudeFace unconditionally in the else branch), so if the user later switches to Face mode and selects faces, the still-armed tool WILL fire on the next viewport click via input_viewport.rs:1868. It is latent, not permanently inert — a minor cross-mode state-leak wrinkle, not a second bug. The user-facing defect is unchanged and fully as claimed: in vertex or edge mode E is a silent no-op with zero feedback. Additionally worth recording for the audit: the same dead-key shape applies to I (inset) at key_dispatch.rs:33/:39, and poly_convert_selection's all-elements rule (correct Blender parity in itself) is what forecloses the only plausible workaround, so 'add a selection-promotion fallback' is NOT the right fix — the real fix is implementing extrude_vertices / extrude_edges in the kernel, since nothing in POLY_POLISH_PLAN.md or POLY_FOUNDATION_PLAN.md even tracks them as a known gap.

### Mirror modifier — axis parameter  — `broken`

* **Severity:** blocker | **Verdict:** CONFIRMED
* **Where:** field: PolyModifier.mirror_axis: u8 (core_math/src/scene_graph.rs:321, doc-commented `0=X, 1=Y, 2=Z`); reader: HalfEdgeMesh::mirrored (core_math/src/half_edge.rs:4060-4066 and the merge-plane distance at :4074, both `match axis { 0=>X, 1=>Y, _=>Z }`); writer A: properties_poly.rs:352-357 (bitmask); writer B: poly_add_mirror_modifier (app/src/symmetry.rs:234, `axis.min(2)` = index) reached from the Alt+X symmetry pie

**What it actually does.** TWO WRITERS DISAGREE WITH THE READER AND WITH EACH OTHER. The kernel reads mirror_axis as an INDEX (half_edge.rs:4061-4065). symmetry.rs:234 correctly writes an index. But the properties panel treats it as a BITMASK with three independent X/Y/Z checkboxes that XOR bits 1/2/4 (properties_poly.rs:355-357). Concrete mis-mapping through the panel: tick X → mirror_axis=1 → kernel mirrors **Y**; tick Y → 2 → falls to the `_` arm → mirrors **Z**; tick Z → 4 → `_` → Z (right only by accident); tick X+Y → 3 → `_` → Z only, so multi-axis mirror is silently impossible even though the UI presents three combinable checkboxes. The default PolyModifier::default() sets mirror_axis=0 (scene_graph.rs:347) = kernel-X, yet the panel renders ZERO checkboxes ticked, so a freshly added Mirror modifier visibly mirrors on an axis the UI claims is off. Cross-writer corruption too: the Alt+X pie's 'mirror Y' writes 1, which the properties panel then displays as 'X checked'. The bug is invisible to the test suite because the mesh_sync tests only cover Array/Triangulate/Decimate/Bevel — no Mirror-through-the-panel oracle exists.

**Gap vs Blender.** Blender's Mirror modifier (Ctrl+A → Mirror / modifier panel) has genuinely combinable Axis X/Y/Z toggles — ticking X and Y produces a 4-way mirror in one modifier. AZRA's UI promises exactly that and cannot deliver it: the u8 field is an index, so only one axis is representable at all. Also missing vs Blender: Bisect X/Y/Z, Flip X/Y/Z, Mirror Object (arbitrary pivot — note the kernel already HAS mirrored_across(origin, normal, ...) at half_edge.rs:4136 which could serve this, but the modifier never calls it), Clipping, and Mirror U/V + Offset for UVs.

**Verifier correction (authoritative).** Mirror modifier — axis parameter [BROKEN, blocker]. The u8 `mirror_axis` has TWO incompatible encodings live in the codebase and no translation layer. Kernel = INDEX: half_edge.rs:4060-4066 `match axis { 0=>X, 1=>Y, _=>Z }`, with the merge-plane distance at :4074 matching the same way. Consumer mesh_sync.rs:233 passes `m.mirror_axis` RAW to `mirrored()` — no decode exists anywhere (verified by grepping all of core_engine). Writer A (correct) = symmetry.rs:234 `m.mirror_axis = axis.min(2)`, reached from the Alt+X symmetry pie via sym_pie.rs:427 `SymMode::Modifier`, where sym_resolve (sym_pie.rs:476-482) yields a genuine 0/1/2 index. Writer B (wrong) = properties_poly.rs:352-357, which renders three independent X/Y/Z checkboxes reading bits &1/&2/&4 and XORing 1/2/4 — a BITMASK. Resulting panel mis-mapping: tick X -> 1 -> kernel mirrors Y; tick Y -> 2 -> `_` arm -> Z; tick Z -> 4 -> `_` -> Z (right only by accident); tick X+Y -> 3 -> `_` -> Z only. So multi-axis mirror is silently impossible even though the UI presents three combinable checkboxes — the field is an index and cannot represent more than one axis. Default PolyModifier::default() sets mirror_axis=0 (scene_graph.rs:347) = kernel-X, yet the panel renders ZERO boxes ticked, so a freshly added Mirror modifier mirrors on an axis the UI shows as off. Cross-writer corruption: the Alt+X pie's "mirror Y" writes 1, which the panel then displays as "X checked". SCOPE CORRECTION (the claim slightly overstated): the modifier is not wholly unusable — single-axis mirror works correctly through Alt+X, and Z-alone happens to work through the panel. What is genuinely impossible is multi-axis mirror; the remainder is silent axis mis-mapping. Severity remains blocker because the properties panel is the discoverable path (Mirror is offered in the Add Modifier combo at properties_poly.rs:302, a list whose own comment states it contains only working live-apply arms), 4 of 7 reachable panel states are wrong, and mirror_axis feeds the modifier-stack hash at mesh_sync.rs:203 — so a bitmask value such as 3 persists into the .fl4 and stably re-evaluates to the wrong axis on reload. Invisible to CI: mesh_sync.rs has only three tests (Array/Triangulate/Decimate+Bevel-noop); no Mirror oracle exists. Blender gap (vanilla, not an addon): the Mirror modifier has genuinely combinable Axis X/Y/Z (ticking X and Y gives a 4-way mirror in one modifier), plus Bisect X/Y/Z, Flip X/Y/Z, Mirror Object (arbitrary pivot — note the kernel already has mirrored_across(origin, normal, merge, threshold) at half_edge.rs:4136, used by symmetrize, which the modifier never calls), Clipping, and Mirror U/V + Offset for UVs. Fix direction: pick ONE encoding. A bitmask is the Blender-parity choice, requiring mirrored() to loop over set bits (or the modifier to call mirrored_across per axis) and symmetry.rs:234 to write `1 << axis`; both changes must land together, and since mirror_axis is a serialized bincode field, existing saves storing index values need a migration or the reinterpretation must be made value-compatible.

### MISSING: Extrude Vertices / Extrude Edges (E in Vertex or Edge select mode; mesh.extrude_vertices_move / mesh.extrude_edges_move)  `E (in Vertex or Edge mode)`

* **Severity:** blocker | **Verdict:** CONFIRMED
* **What it does.** E on selected vertices creates new verts joined by new edges; E on selected edges creates new edges plus the quad faces bridging them.
* **Why it matters.** This is how you build a surface from nothing: place verts, extrude an outline, extrude the outline into a strip, then keep pulling. Every retopology and low-poly workflow starts here. In AZRA the only way to add geometry is to spawn a primitive and cut it down — you cannot draw a shape and pull it into a surface. Worse, the key is silently dead: key_dispatch.rs:18 arms PolyTool::ExtrudeFace and input_viewport.rs:1868 then refuses it because selected_faces is empty, with no toast, so the user sees the tool 'activate' and then do nothing.
* **Confirmed absent by searching:** grep -rniE 'extrude_vertices|extrude_edges|extrude_vert|extrude_edge|dupli_extrude' over app/src and core_math/src = 0 hits. Kernel has only extrude_face (half_edge.rs:1041) and extrude_region (:1127), both face-domain. PolyEdit (mesh_ops/mod.rs:269-316) has no vertex- or edge-domain extrude variant. key_dispatch.rs:11-20 gates E on PolyWorkMode::Face.

### MISSING: Boolean MODIFIER (Properties → Modifiers → Boolean)  `Modifier stack (Ctrl+A applies); the destructive edit-mode equivalent is the Bool Tool addon`

* **Severity:** blocker | **Verdict:** CONFIRMED
* **What it does.** A non-destructive, live CSG modifier: pick an Object or Collection operand, choose Intersect/Union/Difference, and pick a Solver — Fast, or Exact with Self Intersection and Hole Tolerant sub-options. The cutter stays a separate editable object; moving it re-cuts in real time, and the modifier can be reordered against Subdivision, Bevel, Mirror, etc.
* **Why it matters.** This is the single largest structural gap in my area. AZRA's boolean is destructive-only: poly_boolean_execute (app/src/poly/boolean.rs:518-549) overwrites the target mesh in a transaction and DELETES the cutter node (:540-542) unless keep-cutter is set. There is no Boolean variant in PolyModifierType (core_math/src/scene_graph.rs:301-310), so a live boolean is not even representable. The consequence for hard-surface work is severe: every panel cut, every bolt hole, every vent is a one-way commit — adjusting a cut's position means undoing back past it and redoing all subsequent work. Combined with the f32 BSP solver that the kernel itself documents as 'NOT exact-arithmetic robust' (mesh_boolean.rs:18-20) and the strict all-or-nothing install guard (:146-154, which correctly REFUSES bad results rather than shipping them), a user who hits a refused boolean has no live operand to nudge and retry with. A Boolean modifier would also make the existing strict guard far more tolerable, since a failing live boolean can simply be adjusted rather than lost.
* **Confirmed absent by searching:** Grepped core_math/src/scene_graph.rs for the full PolyModifierType enum (:301-310 — Subdivide, Mirror, Solidify, Smooth, Triangulate, Decimate, Array, Bevel; no Boolean). Grepped app/src for: Boolean modifier, PolyModifierType::Boolean, live_boolean, nondestructive boolean, bool_modifier. The mesh_sync.rs:231-274 match is exhaustive over the 8 variants, confirming no hidden ninth.
