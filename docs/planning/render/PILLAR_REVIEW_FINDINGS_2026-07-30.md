mechanism. Those corrections are the trustworthy version — reviewers were asked for quantified impact
and some extrapolated rather than measured. Treat any unqualified "N ms" in an evidence block as an
estimate unless the verifier confirmed it.

1. ~~**Smart Mirror is broken twice over**~~ — **PARKED, owner-directed 2026-07-30.** See

3. **Voronoi non-triplanar emits invalid WGSL** (`shader_nodes/graph.rs:1157`) — **I reproduced this
   at HEAD.** Compiling a Voronoi node in each projection mode:

   ```
   VOR ProjectionStyle::None:      PARSE FAIL — error: redefinition of `n1_dist`
   VOR ProjectionStyle::Triplanar: OK
   ```

   So it is live: set a Voronoi node to any single-plane projection and the whole material's GPU bake
   fails validation and silently falls back to CPU (7.6× at 256², 67× at 512²). This is a **10th
   instance of the exact class G1/G2 were built to eliminate**.

   **And it exposes a real gap in the new G2 gate.** `every_nodetype_generates_valid_wgsl` builds each
   node with its **default** projection, and Voronoi's default is Triplanar — the passing case. The
   gate is exhaustive over *node types* but not over *node configuration*, so any bug reachable only
   via a non-default enum hides from it. That is the same shape as the original problem: a test that
   covers the happy path and reports green.

   `NoiseType`, `DecimateMode`-like selectors) inside the existing per-NodeType loop. Cost is a few
   hundred extra compiles — still well under a second — and it is the difference between "every node
   type compiles" and "every node type compiles *however the user set it up*."
4. **`upload_map_16` lands the lo plane on an unrelated map's slot** (`material_textures.rs:482`) when
   the channel was previously uploaded as 8-bit — silent cross-map corruption.
5. **Flip Normals silently refuses on any mesh ever deleted from** (`mesh_ops/mod.rs:626`) — the
   free-list makes the mesh "sparse" and the op no-ops. A dead menu item for most real meshes.

## Smart Mirror — PARKED, rebuild later (owner-directed 2026-07-30)

> **Owner:** *"the smart mirror is an old tool that never work really, we should rebuild it to be an
> action for mirror in sdf — but not now, put it on hold."*

**Status: do NOT fix `mirror_actions.rs:314/:321`.** The two defects the review found are real and
correctly diagnosed, but they are symptoms of a tool that never worked. Patching them would spend
effort stabilising something scheduled for replacement, and would make the eventual rebuild harder by
adding code someone must then justify deleting.

**Keep the findings as the rebuild spec.** They are precisely the two things the replacement must get
right, and both are the kind of defect that is easy to reintroduce:

* **Never express a mirror as a negative scale on an SDF prim.** `primitives.rs:882` evaluates
  `d * self.scale.x.min(self.scale.y).min(self.scale.z)` — a negative component makes the whole
  distance negative, which inverts inside/outside. The solid renders inside-out in the bake, the GPU
  eval, and the outline simultaneously. A mirror must be a **reflected transform** (or a body-level
  `mirror_flags`, which already exists and which the Body Mirror AABB rule in CLAUDE.md already
  accounts for), never a sign flip on scale.
* **Never push to `self.scene.primitives` directly.** `mirror_actions.rs:321` does
  `s.scene.primitives.push(inst)`, writing the flat GPU cache with no scene-graph write. Per CLAUDE.md
  the graph is the source of truth and `primitives` is a read-only cache, so the next
  `sync_flat_cache()` silently destroys the instances. The rebuild goes through the graph and the
  Structural Mutation Checklist (mutate graph → `recalculate_body_origin` → `sync_flat_cache` →
  `mark_node_body_vol_dirty`), inside a `transaction()`.

### One thing to decide before the rebuild: the live hazard

The broken path **is reachable today**. `input_keyboard.rs:223` routes `Alt+X` to the Symmetrize pie
only when `active_poly_nid().is_some()`; the comment at `:222` states the split explicitly —
*"Context-split: SDF Alt+X is NOT poly, so it falls through to Smart Mirror further down."* So on an
**SDF body**, Alt+X still reaches the broken tool and can produce an inside-out solid plus instances
that vanish on the next cache sync.

Since a fix is off the table, the honest interim options are:

* **(a) Fail closed** — disable the SDF Alt+X → Smart Mirror route with a toast ("Mirror is being
  rebuilt"). One line, removes a user-visible corruption path, and is the guard CLAUDE.md's No-Hacks
  rule explicitly permits ("a documented temporary guard that fails closed").
* **(b) Leave it** and accept that anyone pressing Alt+X on an SDF body gets a broken result.

**Recommend (a)** — but it is the owner's call, and it is deliberately *not* being done as part of
this review. Raising it because "park the rebuild" and "leave a corruption path armed" are different
decisions, and only the first was made.

## Pillar: SDF modeling

### SDF→Voxel stamp rebuilds the entire BodyField (deep-cloning every prim) once per voxel

* **Lens:** perf | **Category:** performance | **Reviewer confidence:** high
* **Location:** `core_engine/core_math/src/field_eval.rs:463`

**Evidence.** `SceneEvaluator::eval_body_internal` (field_eval.rs:459-464) calls `BodyField::from_graph(self.graph, body_nid)` on EVERY invocation, then throws the result away. `from_graph` → `build_scope` (field_eval.rs:303-331) walks `resolve_child_order` and does `let mut sp = p.clone()` for every visible prim in the subtree, recursing into nested sub-bodies. An `SdfPrimitive` clone is NOT a memcpy: the struct (primitives.rs:165-275) owns `name: String`, `material: PbrMaterial` (which itself owns `name: String`, pbr_material.rs:414), `blend_curve: BlendCurve` (owns `points: Vec<BlendCurveKnot>`, modifiers.rs:397), `material_dna: MaterialDna` (owns `rules: Vec<DnaRule>`, material_dna.rs:203), plus `modifiers: Vec<Modifier>`, `sculpt_layers: Vec<SculptLayer>`, `clip_curves: Vec<ClipCurve>` — ≥4 heap allocations per prim clone, more when the stacks are non-empty.  I greped for callers. `eval_body` has exactly ONE production caller (all other hits are #[cfg(test)]): `properties_sdf.rs:1786`, inside the closure passed to `voxel.grid.fill_from_sdf(...)` at properties_sdf.rs:1783. That closure is invoked once per voxel by the triple loop at voxel_sculpt.rs:2439-2443 (`let d = sdf(p);` at :2443). The feature is live UI — the "Stamp into Active Sculpt" / "Carve" buttons at properties_sdf.rs:774-782 call `stamp_sdf_into_active_sculpt`, and the whole thing runs synchronously on the frame thread (no rayon, no background job). `cpu_raymarch` (field_eval.rs:569) has no production callers — that path is test-only, so I am NOT claiming it.

**Impact.** For a stamp whose bounded sweep window is 128³ (≈2.1M voxels — modest for a sculpt grid; the unbounded fallback at voxel_sculpt.rs:2434 sweeps the whole res³) with a 10-prim SDF body, this is 2.1e6 × 10 = 2.1e7 prim clones ≈ 8.4e7 heap allocations, plus 2.1e6 recursive graph walks of `resolve_child_order`. The allocator traffic dominates the actual SDF math by one to two orders of magnitude, and it blocks the UI thread for the entire duration (multi-second freeze on a large grid). The result of every rebuild is byte-identical — the scene graph is not mutated inside the loop.

**Fix.** Hoist the field out of the per-sample path. `BodyField` is documented as "Owned + Send — safe to build once on the frame thread and evaluate on rayon workers" (field_eval.rs:170-171), which is exactly the intended usage. At the call site (properties_sdf.rs:1779-1791) build `let field = BodyField::from_graph(&self.scene.scene_graph, sdf_nid);` once before `fill_from_sdf`, and have the closure do `field.eval_or(self.scene.scene_graph.effective_world_to_local(sdf_nid, world_p), f32::MAX)` — matching what `eval_body_internal` does, minus the rebuild. Structurally, the cleaner fix is to give `SceneEvaluator` a lazily-memoized per-body `BodyField` cache (e.g. `RefCell<HashMap<NodeId, BodyField>>`) so every `FieldEvaluator` consumer gets the fix and the trap cannot be re-fallen-into; the memo is safe because `SceneEvaluator` borrows the graph immutably for its whole lifetime. Since the field is `Send`, the voxel sweep can additionally be rayon-parallelised over z-slabs — no GPU port needed and no readback risk.

**Verifier correction (authoritative).** The defect and mechanism are correct as written; only the magnitude is overstated as if measured. Corrected claim: SceneEvaluator::eval_body_internal (field_eval.rs:463) rebuilds the entire BodyField — deep-cloning every visible prim in the subtree via build_scope's `p.clone()` at field_eval.rs:310, with recursion into nested sub-bodies at :327 — on EVERY sample. Its one production caller is the per-voxel closure at properties_sdf.rs:1784-1787, invoked once per swept voxel by the triple loop at voxel_sculpt.rs:2439-2443, synchronously on the frame thread. The sweep IS AABB-bounded (properties_sdf.rs:1749-1773 → voxel_sculpt.rs:2423-2432), so the true voxel count scales with the stamped body's extent rather than always hitting 128³/res³; the "2.1e7 clones / multi-second freeze" figure is an illustrative upper bound, not a measurement. What does hold unconditionally: the smoothstep01 cull at voxel_sculpt.rs:2445-2446 runs AFTER sdf(p) at :2443, so no swept voxel escapes the rebuild, and each rebuild is byte-identical because the graph is never mutated inside the loop. Fix as proposed — hoist `BodyField::from_graph` above fill_from_sdf, per the type's own doc contract at field_eval.rs:170-171 ("build once on the frame thread"), which is what all ~11 other call sites in the codebase already do.

### trigger_bake deep-clones the whole prim subtree six times per dirty body per drag frame

* **Lens:** perf | **Category:** performance | **Reviewer confidence:** high
* **Location:** `core_engine/app/src/body_volume_cache/bake_dispatch.rs:429`

**Evidence.** Inside `trigger_bake`'s per-body loop (bake_dispatch.rs:314-1558), one dispatch for a single dirty body performs these independent full-subtree prim clones, each via `collect_body_prims_recursive` (bake_utils.rs:64-99, whose inner loop does `let mut p = p.clone()` at :82):  1. `:429` `let prims = collect_body_prims_recursive(sg, body_nid)` — clone #1 2. `:446` `let local_prims = prims.clone()` under `BODY_LOCAL_PRIMS` (true in production) — clone #2, a straight copy of the Vec just built 3. `:469` `compute_template_hash(sg, body_nid)` → `collect_body_prims_recursive` again at bake_utils.rs:584 — clone #3 4. `:1455` `body_needs_cpu_full_stack_bake(sg, body_nid)` → `collect_body_prims_recursive` at bake_utils.rs:154 — clone #4 5. `:1534` `body_needs_cpu_full_stack_bake(sg, body_nid)` a SECOND time, same arguments, same frame — clone #5 6. `:1542` or `:1553` `BodyField::from_graph(sg, body_nid)` on the sparse arms → clones every prim again via build_scope — clone #6 (and `:1313` adds another on the frozen-partial arm)  Clones #4 and #5 are the most wasteful: `body_needs_cpu_full_stack_bake` clones the subtree only to call `p.needs_cpu_full_stack_bake()` (primitives.rs:980-999), which reads nothing but `self.modifier` and `self.modifiers` — a pure `&self` predicate that never needed an owned prim. `body_soft_feature_size` (bake_utils.rs:322) has the identical shape: it clones the subtree to read `p.visible` and `p.operation.blend_k()`.  This is on the live drag path, not a rare one. The partial-bake arm deliberately bypasses the 40ms debounce — bake_dispatch.rs:331-344 skips the debounce whenever `any_has_regions`, with the stated rationale "Partial bakes over small sub-regions are cheap enough to dispatch every frame for real-time cache updates during drag" — so this runs at frame rate for the whole gesture.

**Impact.** ~6× the necessary prim-cloning on the frame thread every drag frame. With a 20-prim body that is 120 prim clones ≈ 480+ heap allocations per frame per dirty body, plus 3 redundant recursive graph traversals and 2 redundant `hash_prim_slice` walks. The existing `[TriggerBake] {:.1}ms` warning at :1572 fires above 5ms, and the code's own comments record measured 5-22ms multi-prim-drag triggers (chunked_dc.rs:1467). Against a 12ms CPU/frame FrameScheduler target, this is a meaningful slice of the budget for work whose output is discarded.

**Fix.** Three cheap, independent fixes, no architecture change: (a) delete clone #2 — under `BODY_LOCAL_PRIMS` the `prims.clone()` at :446 is pure waste; move `prims` and use the legacy branch's output only in the `else`. (b) Hoist `body_needs_cpu_full_stack_bake` to a single call before the `use_gpu` branch at :1456 and reuse the bool at :1534 (`force_cpu_mod` is already computed and in scope). (c) Change `body_needs_cpu_full_stack_bake` and `body_soft_feature_size` to take the already-collected `&[SdfPrimitive]` (both callers in trigger_bake have `local_prims` in scope), or add a borrowing `collect_body_prims_recursive_refs` returning `Vec<&SdfPrimitive>` for the read-only predicates. (d) `compute_template_hash` can take `&local_prims` the same way — its body (bake_utils.rs:576-596) only hashes.

**Verifier correction (authoritative).** Narrow the claim from "six clones, ~6x waste, costing the measured 5-22ms" to "roughly four removable clones of unmeasured but non-trivial cost." Three corrections. (a) Clone #6 is NOT waste: BodyField::from_graph at :1542/:1553 builds the field snapshot shipped to a background classify worker that has no graph access — the comments at :1550-1552 state this dispatch-time-provenance requirement explicitly. It is a required payload, as is the :1313 partial-arm equivalent. That takes the honest count to ~4 removable clones (#1+#2 collapse to one, #3, #4, #5). (b) The impact citation misattributes its own headline number: the finding leans on "the code's own comments record measured 5-22ms multi-prim-drag triggers," but chunked_dc.rs:1313, :1468 and :3678 attribute the [TriggerBake] 5-22ms logs explicitly to the frozen-index window-walk brick classify (9 x P field evals per sentinel brick), NOT to prim cloning. The clone cost is real but unmeasured and is a much smaller slice of that budget than the classify walk. (c) Two file paths are wrong: the helper is core_engine/app/src/bake_utils.rs (not body_volume_cache/bake_utils.rs), and the measurement comment is core_engine/core_math/src/chunked_dc.rs:1468 (not app/src/chunked_dc.rs:1467, which does not exist). The defensible residue is the proposed fixes (a) and (b): delete the dead prims.clone() at bake_dispatch.rs:447 and reuse the already-bound force_cpu_mod at :1534 instead of recomputing it. Both are provably safe, local, and independent of the overstated framing; fix (c), changing the read-only predicates to borrow &[SdfPrimitive], is a sound follow-up.

### body_content_id rebuilds and rehashes the full prim subtree twice per frame per mesh-modifier body

* **Lens:** perf | **Category:** performance | **Reviewer confidence:** high
* **Location:** `core_engine/app/src/mesh_presentation.rs:850`

**Evidence.** `ensure_body_mesh_mod_displays` (mesh_presentation.rs:1764) is called unconditionally every frame from the update loop — app_update.rs:472, inside `if self.cache.use_body_vol_cache && !mesh_dragging`. For each body passing `body_needs_display_fold` it calls `sync_body_mesh_mod_display_ex(nid, false, true)` (:1792).  That function computes the display stamp TWICE before it can decide whether the cached fold is warm: `:1613` `stamp_interactive = self.mesh_mod_display_stamp_for(nid, &records)` and `:1615` `stamp_quality = self.mesh_mod_display_stamp_for(nid, &records)` (the two differ only by the `detail_lo_interactive` flag toggled around them). `mesh_mod_display_stamp_for` (:869) opens with `self.mesh_mod_base_key(nid).hash(&mut h)` at :877, and `mesh_mod_base_key` (:848) calls `crate::bake_utils::body_content_id(...)` at :850. `body_content_id` (bake_utils.rs:434-460) does `collect_body_prims_recursive` (full subtree deep clone) then `hash_body_source` → `hash_prim_slice` (bake_utils.rs:655-760), which walks every prim field plus its entire `modifiers`, `sculpt_layers` and `clip_curves` vectors. Then :1732 computes the stamp a THIRD time on the fold path, and :1807 a fourth on the quality-settle re-arm.  Scope check (I verified this rather than assuming it is universal): `use_detail_weighted_lo` defaults **false** (body_volume_cache/mod.rs:744), so `body_needs_display_fold` (:170-181) returns true only for bodies with active mesh modifiers. So the cost is per mesh-modifier body, not per body — but it is unconditional per frame for those, including when nothing changed and the very next check at :1642 returns `warm` and does nothing.

**Impact.** 2-4 full subtree prim clones + 2-4 full `hash_prim_slice` walks per frame, per SDF body carrying a mesh-modifier stack, purely to conclude "nothing changed". For a 20-prim body that is 40-80 prim clones (≥160 heap allocations) and 40-80 deep hash walks every single frame at idle. It scales linearly with the number of mesh-modifier bodies in the scene, which is exactly the case a production scene hits. The function already carries a 10ms `BUDGET_MS` and a 1-fold-per-frame cap (:1783-1788), but that budget guards the FOLD — this hashing happens before the cap can help, on every body in the filtered list.

**Fix.** Memoize `body_content_id` per (NodeId, graph-revision). The scene graph mutation path is already funnelled through `write_prim()` / `mirror_prim_to_graph()` / `mark_prim_dirty()`, so a monotonically-incrementing structural revision counter is cheap to maintain and gives a sound cache key; store `(revision, BodyContentId)` in `CacheState` and invalidate on bump. That single memo also fixes the redundant `body_content_id` calls in `raster_mesh_prep.rs:73`, `:310` and `app_poll_gpu.rs:871`. As an immediate local fix, hoist `mesh_mod_base_key(nid)` to one call in `sync_body_mesh_mod_display_ex` and pass the u64 into `mesh_mod_display_stamp_for` — the two stamps at :1613/:1615 differ only in one bool and provably share the same base key.

**Verifier correction (authoritative).** Two corrections; the finding's core survives both.  1. THE PER-BODY MULTIPLIER IS 2, NOT "2-4", on the idle frame the impact statement describes. The `folded >= 1` cap (mesh_presentation.rs:1788) breaks the loop only AFTER a fold actually succeeds. On an idle/warm frame nothing folds, so the loop never breaks early and `sync_body_mesh_mod_display_ex` runs for EVERY mesh-modifier body — but each such body exits at the `warm` return (:1642-1645) having paid exactly two `body_content_id` calls (:1613, :1615). The third and fourth stamps (:1732 fold path, :1807 quality re-arm) are reachable at most once per frame TOTAL, since both sit behind the 1-fold-per-frame cap. So idle cost = 2 full subtree clones + 2 deep hash walks per mesh-modifier body per frame (for a 20-prim body: 40 prim clones, ≥120 heap allocations, 40 deep hash walks), scaling linearly with mesh-modifier body count. The "40-80 clones / 2-4 walks" figure is roughly 2x overstated.  Critically, this correction does NOT weaken the central claim — it sharpens it. The cap and the 10ms BUDGET_MS gate the FOLD; the stamp hashing happens strictly before either can intervene, which is precisely what the finding asserts.  2. Scope claim verified as stated and worth keeping: `use_detail_weighted_lo` really does default false (body_volume_cache/mod.rs:744), so `body_needs_display_fold` (:170-181) returns true only for bodies with active mesh modifiers. The reviewer checked this rather than assuming universality, and it is correct. Note the latent amplifier: if a user enables Detail LO in Render properties (:1446-1449 flips it), `body_needs_display_fold` becomes true for EVERY top-level SDF body and the cost goes scene-wide.  The proposed fix is sound. The cheap immediate half — hoist `mesh_mod_base_key(nid)` to one call and pass the u64 into `mesh_mod_display_stamp_for` — is provably safe: `mesh_mod_base_key` reads nothing that the `detail_lo_interactive` toggle at :1612/:1614 mutates, so the two stamps demonstrably share one base key. That alone halves the idle cost with no new cache-invalidation surface. The fuller (NodeId, graph-revision) memo additionally covers raster_mesh_prep.rs:73/:310 and app_poll_gpu.rs:871, but needs care: any revision counter must be bumped by every mutation path that `hash_prim_slice` is sensitive to — including `lab_operand_gen`, child-order permutation via `reorder_child_in_body`, and elongation — or it reintroduces exactly the stale-hash class documented in bake_utils.rs:430-433 and :666-670.

### Chunked DC allocates a Vec per grid cell for edge crossings

* **Lens:** perf | **Category:** performance | **Reviewer confidence:** medium
* **Location:** `core_engine/core_math/src/chunked_dc.rs:1760`

**Evidence.** In `extract_chunk_from`'s Step 1 dual-vertex loop (chunked_dc.rs:1745-1830), line 1760 does `let mut crossings: Vec<(Vec3, Vec3)> = Vec::new();` INSIDE the innermost `plx` loop, then pushes at :1780. The capacity is statically bounded at 12 — a cube cell has exactly 12 edges (`for &(a, b) in &EDGES` at :1761) — so it can never exceed 12 entries and is a textbook fixed-array case. Each surface-crossing cell therefore performs a heap allocate + at least one realloc growth + free, in a loop that visits every cell of every chunk.  I must be honest about reachability, because it changes the severity: I traced the route decision and this is NOT the production display path. `dc_mesh_route` (cache_state.rs:338-350) returns `CpuChunkedOracle` only when `gpu_sdf_mesh` is false, and that flag defaults **true** (cache_state.rs:429), with `gpu_sdf_mesh_resident` also defaulting true (:437). ### Flip Normals silently refuses on ANY mesh that has ever been deleted/dissolved from (free-list makes it "sparse")

* **Lens:** bugs | **Category:** bug | **Reviewer confidence:** high
* **Location:** `core_engine/core_math/src/mesh_ops/mod.rs:626`

**Evidence.** `compute()` picks the undo tier at :436 with `dense = m.vertices.len()==m.vertex_count() && m.faces.len()==m.face_count()`, i.e. all three free-lists empty. `element_tier = is_element_delta() && dense` (:437). **Impact.** User-visible workflow break with a misleading message. On a fresh cube, Shift+N-style Flip Normals works. **Verifier correction (authoritative).** One overstatement must be corrected: the claim that after one delete "the mesh is sparse forever (until a from_polygons rebuild)" is WRONG. Option (b) (batch the whole selected face set into ONE op, then validate) is the stronger fix and matches Blender: it also fixes the inverse defect the finding correctly identifies, where the dense/element tier installs a mesh that is_manifold would reject. ### raster_data_ngon computes per-corner smooth normals from a fan that stops at the first boundary edge

* **Lens:** bugs | **Category:** bug | **Reviewer confidence:** medium
* **Location:** `core_engine/core_math/src/poly_mesh.rs:158`

**Evidence.** For each face corner, `raster_data_ngon` averages face normals over `mesh.vertex_fan(fv[k])` (:158), filtered to faces within AUTO_SMOOTH_ANGLE_DEG of this face (:162). `vertex_fan` (half_edge.rs:381-398) starts at `vert(v).half_edge` and walks `cur = he(twin).next`, with `if twin == NO_TWIN { break; }` at :391 — a one-directional walk that terminates at the first boundary edge. On an OPEN mesh (any mesh after Delete Faces / Delete Only Faces / a plane primitive / an unclosed boolean result) a boundary vertex's fan therefore covers only the arc from the arbitrary `vert.half_edge` start to the first boundary, not the full incident set. Which faces are covered depends on which half-edge happens to sit in `vert.half_edge` — and that pointer is REASSIGNED by the repair loops in delete_face (:1489-1494), delete_face_only (:1547-1552), join_edge_kill_vert (:3446-3451) and merge_vertices_to (:1405-1410), each of which picks `the first live half-edge sourced at v` by linear scan. `raster_data_ngon` is the live poly display path — app/src/poly/mesh_sync.rs:111 and app/src/raster_mesh_prep.rs:162,182. Note the same fan is used by `compute_vertex_normal` (:632-642), which feeds `content_signature` (:881-883), so the shading state is also part of the display cache key.

**Impact.** Shading, not geometry — but it cannot fail loudly. A vertex on an open boundary gets its smooth normal averaged over an arbitrary SUBSET of its incident faces, and which subset changes when an unrelated edit rewrites vert.half_edge. Symptom: shading seams along open borders that shift after a delete/merge elsewhere in the mesh, with no error and no way for the user to attribute it. The 30-degree cluster filter at :162 bounds the error (a wildly wrong normal cannot be admitted) and the `length_squared() < 0.25` fallback at :167 catches total collapse, so this degrades quality rather than producing garbage — which is precisely why it has survived. The module's own doc at :128-131 flags the fan-vs-cluster divergence as "rare; upgrade if an oracle case ever demands it" but does not mention the boundary truncation at all.

**Fix.** Do not derive the corner fan from `vert.half_edge`. The corner already knows its own half-edge — `raster_data_ngon` iterates faces and has `fid`, so walk the incident faces starting from THIS face's corner half-edge in both rotational directions (forward via twin.next, backward via prev.twin), stopping at boundaries on each side. That makes the result independent of the arbitrary disk-pointer start and covers the full incident set on an open mesh. `PolyMesh::smooth_corner_normal` (:655-680) has the identical defect — it also fans from `vertex_fan(vid)` — and should share the fixed traversal rather than get a second copy.

**Verifier correction (authoritative).** The core claim stands as written. Two peripheral corrections:  1. The `smooth_corner_normal` (poly_mesh.rs:655) companion defect is OVERSTATED as "identical". It shares the truncating `vertex_fan(vid)` traversal, but it is materially less affected: it seeds `sum = face_n` and `count = 1` and skips `f == fid` (:662-666), so this face's own contribution is guaranteed regardless of where the fan starts — whereas `raster_data_ngon` relies on the fan to include the current face at all (it is saved only by the :167 fallback). It is also on a DIFFERENT path (`PolyMesh::to_raster_data`, gated behind `use_smooth`), not the `raster_data_ngon` path. Still worth sharing a fixed traversal, but it is not an equal-severity second instance.  2. Of the four cited disk-pointer rewriters, `delete_face_only` (:1540-1554) is the weakest trigger — its own comment says "Nothing was freed here, so in the common case every pointer is still live and sourced at its vertex and this loop is a no-op". The strong triggers are `delete_face` (:1482-1496), `merge_vertices_to` (:1405-1410) and `join_edge_kill_vert` (:3446-3451), plus the unconditional reassignments at :1090-1091, :2408 and :3221-3224 which the finding did not cite and which rewrite the pointer with no staleness precondition at all.  Also worth adding to the impact: because `content_signature` (half_edge.rs:871) hashes `f.half_edge` and stored vertex/face normals, an edit that changes only a disk pointer CAN shift the display cache key — so the re-shaded result is recomputed and cached, i.e. the mechanism propagates the arbitrary normal rather than masking it.

### Shared mesh math (merge_meshes / transformed) lives in the app's boolean module and is O(n^2) in the Array modifier

* **Lens:** arch | **Category:** architecture | **Reviewer confidence:** high
* **Location:** `core_engine/app/src/poly/boolean.rs:108`

**Evidence.** `merge_meshes` (app/src/poly/boolean.rs:108) and `transformed` (:34) are `pub(crate)` helpers in the app crate's boolean module. `merge_meshes` is documented at :102 as 'the single canonical mesh-concat helper'. But the poly MODIFIER STACK — pure display math that belongs in core_math — reaches back up into the app boolean module to use them: app/src/poly/mesh_sync.rs:254 calls `crate::poly::boolean::transformed` and :256 calls `crate::poly::boolean::merge_meshes` to implement the Array modifier.  This violates the CLAUDE.md rule 'A function used by multiple systems (noise, SDF eval, transform math, ray casting) lives in a SHARED module (core_math ...) — never inlined in the caller'. The concrete consequence is that core_math cannot use its own canonical concatenator: `poly_mesh::triangulate_mesh` (poly_mesh.rs:192-233) reimplements the same remap-to-positions/rings/ring_mats/from_polygons/write-back-material_id sequence found in merge_meshes:109-141 — the same ~30 lines, the same material-restore-after-rebuild gotcha, with nothing keeping them in sync.  Performance: the Array loop at mesh_sync.rs:250-258 does `result = merge_meshes(&result, &placed)` inside `for i in 1..count`. Each call rebuilds the entire ACCUMULATED mesh through `from_polygons`, so N copies cost O(N^2) face-ring rebuilds rather than O(N). `array_count` is slider-capped 2..=20 (properties_poly.rs:383), so on a 5k-face base a count=20 array does roughly sum(i*5000) for i=1..20 = ~1.05M ring rebuilds per evaluation. This runs inside `apply_poly_modifiers`, i.e. on every display re-sync where the stack hash changed — so it fires on every drag of the Count or Offset slider.

**Impact.** Two copies of the concat-and-restore-materials logic with no forcing function: a fix to one (e.g. the `if i < out.faces.len()` material write-back guard, which is a silent truncation on both) does not reach the other. Plus a user-visible stall when dragging the Array modifier's Count/Offset sliders on a moderately dense mesh, from an accidental quadratic that a single-pass concat removes entirely.

**Fix.** Move `merge_meshes` and `transformed` into core_math (poly_mesh.rs is the sanctioned home for poly runtime logic), re-export or re-point the app's boolean module at them, and have `triangulate_mesh` build on the shared concat instead of its private copy. Then make the Array modifier accumulate ALL copies' positions/rings in one pass and call `from_polygons` ONCE, which is both the O(N) fix and a smaller function than the loop it replaces. Risk: low — pure relocation plus one loop restructure, and the Array behavior is already locked by the Blender oracle test `apply_array_matches_blender_oracle` (mesh_sync.rs:322), which asserts 24 verts / 18 faces / x-span [-1,5] and will catch any regression.

**Verifier correction (authoritative).** The architecture/duplication claim stands as written. Two corrections to the performance framing:  1. COST UNIT is wrong (understated per-iteration, so the "~1.05M ring rebuilds" figure is not meaningful as stated). The finding counts "ring rebuilds" as the cost unit. `from_polygons` (half_edge.rs:4887-4940) actually does, per call over the WHOLE accumulated mesh: a HashMap entry/probe per half-edge for twin linking (:4918-4926), a full `recompute_normals()` (:4936), and in debug builds a `validate_mesh()` pass (:4937-4938).
