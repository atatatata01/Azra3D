## TL;DR — Go First

**Build Approach A's occlusion-ray core, ship it behind ONE global toggle first, then grow it into Approach C's per-light hybrid.** Do not build Approach B (SDF-only march). AZRA already owns every hard part of RTX shadows: a complete, CPU-parity-tested two-level triangle TLAS/BLAS over *all five body types* (`render/src/pt_accel.rs`), a TDR-safe WGSL traversal, an any-hit occlusion query (`pt_occluded`), a per-light traced-shadow reference (`pt_direct_light`), and a bilateral + temporal denoise stack. The RTX feature is therefore ~90% **wiring**, not new rendering research. The single load-bearing blocker is that the accel is gated to `ShadingMode::PathTrace` (`app/src/pt_scene.rs:306`); decouple that and the machinery already built for the path tracer produces production shadows in the raster viewport.

## 1. Recommended Approach + Why (owner-actionable)

**Recommendation: Approach C (per-light "Ray-Traced Shadows" toggle), reached by shipping Approach A's core mechanism first.** These are not competing choices — A is the *engine* (a compute pass that fires occlusion rays against the PT BVH and writes a visibility buffer the deferred lighting consumes); C is the *product shape* (which lights use that engine vs. keep their cheap legacy technique). We ship A wired to a single global switch for the fastest honest visible win — poly/voxel/imported/NURBS objects finally cast point/spot shadows, softly, across the whole scene — then add the per-light routing table that turns it into C. This ordering means the risky core (residency decouple, shared traversal WGSL, denoise) is validated on screen before we spend effort on UI, channel packing, and save-format plumbing.

We reject **Approach B (extend the SDF `soft_shadow` march)** decisively. Its quality on SDF bodies is genuinely excellent and noise-free, but it has a structural coverage ceiling: `scene_sdf` only contains analytical SDF prims, so poly, voxel, imported, and NURBS objects cast **zero** shadow from any point/spot light, forever — and the result is asymmetric (an SDF sphere shadows a poly floor, but a poly cube shadows nothing). That directly contradicts the goal ("ray-traced projected shadows, RTX quality" implies *all* geometry) and contradicts the sun's own CSM path, which already shadows all body types. It would ship a confusing, half-covered shadow model while the flagship RTX capability — a finished BVH one wiring job away — sits unbuilt. **Choose C via A. Never invest in B.** *(Rule check: this composes with the Display Invariant — the RT pass reads the G-buffer and writes only a visibility scalar consumed inside the single deferred view. It is depth-compositing inside one view, NOT a fused multi-object raymarch-over-raster. Not a violation.)*

## 3. Honest Cost / Risk

**Perf.** Shadow rays are the cheapest RT — any-hit occlusion, no shading, no bounce. The PT already traces multi-bounce + per-light NEE shadow rays interactively over this same BVH, so 1–4 occlusion rays/px is a fraction of one PT sample. It is pure GPU compute: ~0 added CPU/frame beyond dispatch, respects the 12 ms budget and the `MAX_*_PER_FRAME` caps. TLAS refit is sub-ms for moving lights/objects (geometry SSBOs untouched). **The real standing cost is residency:** whenever any RT light is active, the accel builds BLAS (capped 4/poll) and holds multi-MB geometry SSBOs in VRAM *even in Object mode*. This MUST be gated on the toggle, with a clean "no RT lights → tear down accel" path, or it is a silent memory/perf tax on every user who never enables the feature. *(Stage 1: the accel residency IS gated on the toggle via Stage 0; the always-resident full-res RGBA16F visibility texture is a small additional cost while any deferred frame renders — a "tear down when off" pass is a Stage-4 polish.)* Also account for sparse SDF ≥512³ bodies: they have no CPU mesh, so their BLAS depends on `pump_pt_sdf_snapshots` settling — a large resident SDF body casts no RT shadow for the first frames (reads as pop-in).

**Denoising is mandatory, not optional.** At the sample counts that keep this real-time (1–2 spp), raw visibility is noisy; the honest cost of the feature is "shadow ray + spatial + temporal," and under-budgeting the denoise makes it look broken at ship. The good news: the entire denoise stack already exists (`pt_denoise.wgsl` bilateral, `temporal_reproject.wgsl` validity mask, deferred `shadow_ao` blur, PT `pt_accum` history) and is reused wholesale — Stage 2 is wiring, not new algorithms.

**No-TAA-yet constraint.** AZRA has no TAA today, so temporal shadow accumulation rides `temporal_reproject.wgsl`'s reprojection validity mask rather than a full TAA history. This is sufficient for a scalar visibility signal but has two consequences: (1) disocclusion edges (newly-revealed geometry behind a moving occluder) fall back to spatial-only denoise for a frame or two and can shimmer; (2) fast light motion boils more than a TAA'd pipeline would. Both are acceptable for v1 and mitigated by the animated blue-noise offset. Full TAA is out of scope here.

**The two locked contracts to respect (highest silent-corruption risk).**
- **`FLOATS_PER_LIGHT=20` is FULL** — slots 16–19 are volumetric fog. Adding `light_radius` / `rt_enabled` / `sample_count` (Stages 3–4) means bumping the stride across `sdf_lighting.wgsl`, `fog_entry.wgsl` `VL_STRIDE`, `serialize_to_gpu`, **and** the locked-layout test at `scene_graph.rs:1943`. Get one wrong and every light misreads — silent, not a compile error. Do this as one coordinated commit. *(Stage 1 avoided this entirely: it reads only the existing point/spot position + type, no new per-light field.)*
- **`LightData` is SERIALIZED** — a new field hits the bincode save-format trap. It MUST ride a `#[serde(default)]` / `FL4ORDER` side-channel, never a bare struct field, or it corrupts every existing `.fl4`. *(Stage 1's `rt_shadows` toggle is runtime-only, not serialized — no trap.)*

**Shader-region discipline.** The shared traversal WGSL must be `#region`-tagged and stripped from deferred-lite (which strips `scene_sdf` today). Any reference leaking outside the region is a parse error across *all* deferred build variants — 25–43 s recompile per mistake. Confine all references to the region. *(Stage 1: `PT_TRAVERSAL` lives in `pathtrace_tri_entry.wgsl`, which the deferred build never includes, so it is stripped by construction; the risk lived in the deferred RT-swap, which was kept OUTSIDE `#region SHADOW_AO`. All Naga variants validated.)*

**Hybrid consistency (Stage 4).** Two shadow techniques coexisting is inherent to C, not a bug: an RT soft-disc penumbra next to a k-based SDF march (fill light) or a CSM sun must stay tonally consistent, or the frame reads as two shadow systems. This is a QA/art-direction burden the owner should expect, and the reason the sun defaults to CSM until RT-vs-CSM tone is dialed in.

## 4. Owner-Facing Control

**Per-light, in the light properties panel:**

- **☐ Ray-Traced Shadows** (toggle). Off = current behavior (CSM for the sun, SDF soft-march for point/spot). On = BVH occlusion rays, all-geometry, soft, denoised. *(Stage 1 ships this as a single global switch in the Render panel — "Ray-Traced Shadows (point/spot)"; Stage 4 makes it per-light.)*
- **Soft Radius** (slider, world units; angular degrees for the sun). 0 = crisp/hard contact shadow. Higher = wider physical penumbra with contact hardening. This is the new `light_radius` field. *(Stage 3.)*
- **Samples** (1–8, default 2). Rays per pixel over the light disc. Higher = less noise / smoother penumbra at higher cost. Auto-drops to 1 during interaction (latched like SSR/fog). *(Stage 4; Stage 1 is implicitly 1.)*

**Sensible defaults:** RT off (no perf/VRAM tax until asked); when enabled, Radius small (near-contact hard), Samples 2. The sun stays CSM unless the user explicitly promotes it to RT for soft area shadows. A global "tear down accel when no RT light is active" is automatic, not a user control.
